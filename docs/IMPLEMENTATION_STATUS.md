## 規則依入學年度取用

`CoreService` 可同時載入多個年度的規則庫：`kb_path` 為預設年度（名單 `cohort` 空白時使用），`extra_kb_paths` 為其他年度；同一年度重複載入時直接報錯。

- 每位學生依名單 `cohort` 使用自己年度的規則庫（`CoreService.ruleset(sid)`）；`student()` 的 `cohort`、`rule_version`、缺課與剩餘課程，以及系辦總表、匯出 CSV、列印明細、人工覆核記錄的規則版本都依該生年度。
- 名單年度沒有對應規則庫時列為 `other_cohort` 異常、不審查，訊息列出現有年度；不套用其他年度。
- 驗證使用測試中由 114 改出的虛構 112 規則庫（`tests/test_cohort_rules.py`），不代表正式規則。網頁（`web.py`）以 114 為預設年度，另載入 `data/` 下所有 `curriculum_im_<年度>.json`；目前只有 114 正式規則，因此實際只有 114。命令列仍只載入 114。
- 學生端規劃與 What-if（`student_api.py`，B 組）尚使用預設年度規則庫，改用 `ruleset(sid)` 屬 B 組「規劃器改用入學年度規則」。命令列批次審查（`app.py`）亦尚未改為多年度。

## AI 解析儀表板

流程：系辦頁「AI 解析儀表板」分頁上傳 PDF 並填學號（去識別化代號）→ Gemini 擷取每列修課紀錄與來源頁碼、原文 → 檢查 → 承辦人逐列對照修正 → 勾選「已對照原文並確認所有警示」（確認人取頁首「承辦人」欄）→ 以確認後的紀錄取代或新增該生資料並重新審查。

- **AI 只擷取**：規則代碼對應到類別用 `dashboard.FORMATS` 固定對照表；判定仍由規則引擎產生。
- **檢查**：欄位格式、重複列、缺來源為錯誤，未修正前不能確認；學分與規則庫不同、文件標示的分段或總實得學分與擷取合計不符（可能漏列）為警示，須勾選確認。無法辨識或沒有擷取到紀錄時為錯誤，不會當成沒有修課紀錄。
- **依入學年度審查**：確認時採用承辦人填的入學學年度，空白時沿用名單年度，再空白才用預設年度；學分檢查與審查都用該年度的規則庫。系統沒有該年度規則庫時，解析結果與確認都列為錯誤，不送入審查、不改資料，也不套用其他年度。
- **確認前不進入審查**：草稿只存在記憶體；確認時伺服器重新檢查，再經 `records.parse_records` 與 `load_data` 套用，任何錯誤都不改變現有資料。
- **服務失敗**：主模型 `gemini-3.5-flash` 持續過載或逾時時改用備援 `gemini-2.5-flash`，結果記錄實際模型及改用原因；全部失敗時列出各模型的失敗原因，可改用上傳 CSV。
- **等待時限**：每個模型的總等待（含重試）有上限，主模型預設 90 秒（環境變數 `GEMINI_TIMEOUT` 可調），備援模型 120 秒，預設最久約 3.5 分鐘就有結果或錯誤（原本最壞可能超過 20 分鐘）。逾時不重試，直接改用備援；過載（429、5xx）只在時限內重試。系辦頁解析中顯示已等待秒數，改用備援時在模型資訊旁標示原因。
- **支援版型**：目前只有虛構示範版型 `demo-v1`（`python -m academic_twin.demo_dashboard` 產生 `data/samples/` 的 PDF 與標準答案）；版面依 2026-10-14 訪談描述模擬，真實格式待取得去識別化範例。不支援掃描影像。
- **只上傳去識別化或虛構文件**：檔案內容會送至 Gemini。
- **雙模型交叉驗證**（`academic_twin/cross_check.py`）：同一份 PDF 由主模型與第二模型（環境變數 `GEMINI_CHECK_MODEL`，預設 `gemini-2.5-pro`）同時擷取，以（科目代碼, 學期）對齊後比對規則代碼、課名、學分、成績（NFKC 正規化，學分與成績比數值）。不一致的欄位、只有一方擷取到的列都列為警示，須勾選確認才能送出；承辦人改成與第二模型一致後不再提示。系辦頁上方顯示「一致 N 列、需優先核對 M 列」。第二模型失敗、或主模型改用備援後與第二模型相同時，照常使用主模型並標示「未交叉驗證」。確認紀錄另記人工修正落在標示列與未標示列的列數、補回的漏列中有幾列曾被第二模型提示（只記數字）。**兩模型一致不代表正確**（可能犯同樣的錯），所有列仍須承辦人確認。
- **原文與頁碼自動核對**（`academic_twin/pdf_text.py`）：以標準函式庫從 PDF 取出逐頁文字（支援 Edge/Chrome 輸出的子集字型與 ToUnicode、Word/Excel 匯出的物件串流與 WinAnsi 字型），文字只在本機比對、不送給 AI。每列原文在宣稱頁為相符；在其他頁警示「頁碼可能錯」；整份找不到警示「可能是 AI 編造」；字詞都在但不相連（常見於表格）另行提示；另檢查課號、學分、成績是否出現在該列原文。比對採 NFKC、不分大小寫並去除空白與標點。全部為警示；PDF 加密、掃描影像或字型無法解碼時只列一則「無法自動核對原文」，不當成不符。

A 組優先 1，僅草擬公開的 `data/sources/im_114_table.pdf`（114 應修科目表）三項要求，全部標示「AI 草稿、未啟用」：

流程：公開 PDF → `llm.generate_json`（JSON schema）→ 每條保留適用年度、來源頁次、原文位置與逐字引用、適用條件、例外及核對事項 → 結構與來源缺漏檢查 → `knowledge_base.from_dict` 重用既有課號、類別與來源關聯驗證 → 與現有 114 JSON 比對 → 人工對照、修正、重新檢查與確認 → 保存已確認草稿。沒有啟用步驟，也不改審查資料、判定或正式交接格式。

- **差異供人工確認**：指定三項逐欄列出相同、欄位不同、草稿漏列、多列；其他 114 要求不算本次漏列。差異顯示「需人工確認」，不當成 AI 錯誤。現有 JSON 含假設，不是完整人工答案；相同也須核對原文。
- **錯誤阻擋**：缺來源頁碼／引用、年度不符、欄位型別錯誤、未支援欄位或規則類型、重複要求、未知課號／類別、非正整數門檻皆不得確認。無法辨識或無要求不能視為成功。此最小版僅支援三項所需的 `all_of`、`category_credits`、`total_credits`。
- **原稿與確認檔分離**：`data/eval/rule_drafts/<id>.json` 保存 AI 原稿；`<id>.confirmed.json` 保存修正後規則、確認人、UTC 時間、修改欄位數與增刪要求數。兩者均不覆寫，確認檔仍為未啟用草稿。檢查操作不覆寫原稿；重啟後可用草稿編號續作。確認前必須明確核對門檻、適用條件、例外、遺漏與差異。
- **介面**：系辦「AI 草擬規則」選擇公開 PDF，可開啟所選原文，逐項看引文、檢查結果與差異；展開 JSON 編輯要求及來源後，按「確認存檔」會先重新檢查並刷新差異，須再核對、勾選後才存檔（確認人取頁首「承辦人」欄）。確認僅存檔。路由限定 `/api/rule-drafts/extract`、`check`、`confirm`；`web.py` 的小範圍路由變更仍需依團隊規則由負責人審查。
- **啟用**：見下方〈規則版本啟用〉；確認存檔本身仍不啟用。


檢查三種提示篩選、與狀態併用的空結果、待辦的承辦單位；對 `DEMO-REVIEW` 第二次紀錄覆核為不採計再撤銷；匯出 CSV 與列印明細。「還原示例資料」只還原這組虛構紀錄。正式示例仍使用 `python web.py`。

規則設定（可選，預設不啟用）：頂層 `repeatable_courses` 為可重複修習課號陣列，可包含依類別採計而未列於課程清單的課號；課程項目可設 `discontinued`、`replacement_courses`、`substitution_office`。替代課必須在規則庫內且不同於原課；承辦單位未知時填「待確認」。清單缺失時不推測可重複或抵修關係。

抵修目前只有提示，尚無個人核准登錄及核准後消除待辦的流程；原必修不因 flags 自動滿足。正式 114 規則的既有假設（含英文門檻）維持原樣，不能以本次測試通過宣稱正式核定。

## 實證比對工具

`academic_twin/evaluate.py`（A 組）把引擎審查結果與承辦人答案比對，並彙整原流程與輔助流程的計時，對應 [實證從第一階段開始](TEAM_PLAN.md#實證從第一階段開始) 的「審查與 flags」「行政時間」兩項指標。**輸出只有彙總數字，不含學號、課程或答案內容**，承辦人可在自己電腦執行後只回傳結果。

```powershell
python -m academic_twin.evaluate audit --records 修課紀錄.csv --roster 名單.csv --answers 答案.csv [--rules 規則庫.json] [--detail] [--out 結果.json]
python -m academic_twin.evaluate timing 計時.csv [--out 結果.json]
```

答案 CSV 每位學生一列（範本：`data/students/demo_flags_answers.csv`）：

| 欄位 | 內容 |
|---|---|
| `student_id` | 學號（去識別化代號） |
| `status` | 承辦人判定：通過／未通過 |
| `unmet` | 未達成的要求編號，分號分隔；通過時留空，未通過時必填 |
| `flags` | 應提示的情況：`overflow`、`repeatable`、`substitution_pending`，分號分隔，沒有時留空 |
| `split` | 開發（可用來調整規則與提示）／驗證（保留到最後，不先看） |
| `source` | 虛構／實務 |
| `confirmed` | Y／N：人工答案是否已由承辦人確認 |

- **分組統計**：依案例來源、開發／驗證、答案是否已確認分開計算，虛構與實務、未確認答案不混在一起。
- **整體狀態**：一致、不一致及「未定」（引擎為 `MANUAL_REVIEW`、`WARNING`，需人工判斷）各自計數，另附「引擎狀態->承辦人判定」對照表。
- **逐條要求**：每條要求的一致、不一致、未定（引擎 `pending`）件數與分母。
- **flags**：每種類型以案件為單位列出正確提示（tp）、誤報（fp）、漏報（fn）與正確未提示（tn）。
- **未審查**：答案中的學生若沒有修課紀錄、入學年度沒有規則庫或不在名單，依原因計數，不算一致或不一致；已審查但沒有答案的件數另列。
- **版本**：每次結果附工具版本、執行時間、案例集合雜湊（修課紀錄、名單、答案三份檔案）與適用的規則版本。不讀覆核紀錄，量測的是引擎本身的判定。
- **格式錯誤**：答案或計時檔有錯時整份不計算並列出行號，包括通過卻列了未達成要求、未通過卻沒列、不認得的提示類型、學號重複，以及要求編號不在該生適用的規則庫。
- `--detail` 另列不一致案例的學號與差異，只供承辦人在本機核對，不可外傳。

計時 CSV 欄位為 `case_id`、`method`（原流程／輔助流程）、`minutes`（含等待 AI、核對與修正）、`order`（全體共用的執行流水號）。結果列出兩種流程各自的件數、中位數、最小與最大值；兩種流程都有的案例另算逐案差距（原流程－輔助流程）的中位數，以及先做原流程的件數。

虛構四案（`demo_flags_*.csv` 與答案範本）的結果：開發組 2 件全部一致、三種 flag 各 1 件正確提示；`DEMO-REVIEW` 引擎列人工覆核，計為狀態未定。**這只證明工具可執行，不是準確率**；實際數據須用承辦人確認的去識別化案例與人工答案，並保留驗證組到最後才執行。

## 規則待確認事項

現有 JSON 已引用 114 年度應修科目表與課程地圖，並非只有早期示意資料；但 `assumptions` 保留以下假設：

- 必選課 IM3029、MA1006 暫設 3 學分；停修是否算「修過」待確認。
- 開課學期部分依建議學期推定，不是實際開課保證。
- 建議先修由順序推論，只影響排課，不影響畢業判定。
- 服務學習門數為暫定解讀；體育 5 學期含大一體育 2 學期，以課名含「大一體育」辨識。
- 通識核心領域依課號第 3 碼推論（CC01–CC04），114 學年度是否適用待確認；R7 以「至少 1 門通識核心」判定，是否須修滿學分、是否指定領域待確認。
- 非 IM 課號可否認列本系選修待確認，目前以人工覆核處理。
- 國文、外文超修及第二外語暫計入外系 12 學分，待確認。

2026-10-10 依說明投影片、111 畢審說明與 113 課程地圖重新審閱，並已改入規則庫：

- R3 必選課改為「修過即可」（`taken_all`）；通過的學分 IM1013、IM3029 計入本系選修，MA1006 計入外系選修並受 12 學分上限（課程 `counts_as`）。

## 限制

系統目前只有 114 學年度規則庫；名單 `cohort` 欄為其他年度的學生列為異常、不審查，空白視為 114。尚未區分學制。網頁上傳的資料只存在伺服器記憶體，重開即回到示例資料。

排課最多模擬 16 學期，使用貪婪法，畢業學期為估計且不保證全域最早。非指定課號需求以「其他學分」補足，尚未逐門安排，也未處理時間衝突、名額及實際開課異動。

來源引用不等於完整覆核紀錄；介面、AI、版本、覆核、匯出依 [主要流程](PROJECT_DESIGN.md) 後續建置。
