# Academic Twin 專案設計與主要流程

更新日期：2026-10-14。本文記錄目前定案架構；尚未建置的流程另行標示。

## 專案目的

將課程規章、課程關係與學生修課紀錄連結起來，提供可追溯的修業進度、畢業資格審查、修課路徑與情境模擬。

## 雙端架構

系統分為學校端與學生端，兩端共用同一套核心，對同一位學生、同一份資料得到相同判定。

| 端 | 使用者 | 主要功能 | 需求文件 |
|---|---|---|---|
| 學校端 | 教務處／系辦承辦人 | 個別學生修業查詢、批次畢業資格審查、例外標註、人工覆核、匯出 | [系辦端業務需求](OFFICE_REQUIREMENTS.md) |
| 學生端 | 在學學生 | 個人修業進度、白話說明、需辦理事項提示、修課規劃與 What-if | [學生端需求](STUDENT_REQUIREMENTS.md) |

```mermaid
flowchart TD
    Dashboard[畢審儀表板／修課紀錄] --> Ingest[資料匯入與解析]
    Ingest --> Audit[審查引擎與例外偵測]
    KB[依入學年度的規則庫] --> Audit
    Audit --> School[學校端：總表、覆核、匯出]
    Audit --> Student[學生端：進度、說明、規劃]
    School -- 覆核與抵修結果 --> Audit
    Graph[課程關係分析] --> Student
    Planner[修課路徑規劃] --> Student
```

依 [2026-10-14 承辦人訪談](MEETING_NOTES_2026-10-14.md)，共用核心需符合以下原則（尚待建置）：

- **規則依入學年度取用**：每位學生依入學當年度的教務章則審查，延畢生亦同；輔系、雙主修、學分學程依申請加修的當年度規則。規則庫需改為依年度載入。
- **資料來源**：承辦人與學生看到的是同一份校務系統畢審儀表板，一條解析流程可同時供應兩端。實際格式待取得去識別化範例後確認。
- **補足校務系統的限制**：校務系統「一個蘿蔔一個坑」，不會跨類別移動超修學分、可重複修習的同課號第二次起不計學分、抵修未辦理前顯示缺課。核心需偵測這些情況並標示，而不是重現系統的判定。
- **用語對照**：校務系統的規則代碼為全校共用，名稱與各系章則用語不同（如必選、應選、M 選 N）。結果需同時呈現系統代碼與章則用語。

## 四個核心模組

| 模組 | 現有檔案 | 職責 |
|---|---|---|
| 規則知識庫 | `academic_twin/knowledge_base.py` | 載入及驗證課程、要求、學分認列政策、來源 |
| 畢業資格審查 | `academic_twin/rule_engine.py` | 分類修課紀錄、計算學分、檢查缺項、產生判定 |
| 課程關係分析 | `academic_twin/graph.py` | 正式與建議先修、前後課程影響及瓶頸分析 |
| 修課路徑規劃 | `academic_twin/planner.py` | 依審查結果、課程圖及情境安排後續修課 |

四個模組在核心能力上並列，但有資料依賴；不代表執行時必須平行運算。`app.py` 是目前串接模組的命令列入口。

```mermaid
flowchart TD
    Rules[課程與畢業規則] --> KB[規則知識庫]
    Records[學生修課紀錄] --> Audit[畢業資格審查]
    KB --> Audit
    KB --> Graph[課程關係分析]
    KB --> Planner[修課路徑規劃]
    Audit --> Planner
    Graph --> Planner
    Audit --> Report[判定與缺項報告]
    Planner --> Plan[修課計畫與情境影響]
```

基本查詢與畢審使用知識庫和審查引擎即可；需要安排未來修課時再接入課程圖與規劃器。學校端以審查為主；課程圖與規劃器主要服務學生端。

## 學校端共同流程

```mermaid

    Validate --> Select[確認適用年度與規則版本]
    Select --> Audit[共用審查引擎]
    KB[規則知識庫] --> Audit
    Audit --> Report[逐人結果與規章依據]
    Report --> Explain[AI 輔助解釋]
    Report --> Review[系辦覆核]
    Explain --> Review
    Review --> Correct[修正資料或認列對應]
    Correct --> Audit
    Review --> Export[確認結果與匯出]
```

上傳介面、AI 整理、規則選擇介面、覆核與匯出仍待建置。此圖描述目標流程。

## 學校端：個別學生修業查詢

1. 取得學生代號、入學年度、系所／學制、修課成績與抵免等資料。
2. 匯入紀錄；AI 文件解析結果須呈現供確認，避免錯讀課號、學分或成績。
3. 檢查資料完整性，確認適用規則；未確認的抵免、舊課號及特殊核准列為疑義。
4. 審查引擎逐條產生已達成數量、缺額、缺課與依據。
5. 顯示缺項、警示與人工確認事項；AI 將結構化結果轉成容易理解的說明。
6. 系辦確認疑義、更新資料後重新審查，提供結果。
7. 如需後續修課安排，再使用課程圖與規劃器。

指定必修列出課號與課名；類別需求列出類別缺額；選修候選課程必須區分「可選」與「全部必修」。

## 學校端：批次畢業資格審查

1. 上傳應屆畢業生名單與修課資料。
2. 按學生分組並核對名單；沒有紀錄的學生進入異常清單，不可漏掉。
3. 每位學生使用其適用年度及規則執行相同審查邏輯。
4. 產生總覽：學生代號、狀態、主要缺項、警示及待覆核事項。
5. 系辦查看單人明細與規章依據，處理課號對應、抵免及特殊核准。
6. 修正後重新審查，記錄確認內容及使用的規則版本。
7. 匯出總覽與逐人缺項明細。

總覽需能一眼看出每位學生缺什麼、超修什麼、哪些項目需人工判斷，承辦人不必逐一點開儀表板。

## 學生端流程

學生端即專案最初的「學業分身」：除了現在的審查結果，還往後推演修課路徑與情境影響。網頁「學生 Academic Twin」與命令列已有畢業進度、到畢業的修課路徑、What-if（某課某學期不修、出國交換）、課程影響範圍與瓶頸課；白話說明、誤判提示與需辦理事項尚待建置。詳細需求見 [學生端需求](STUDENT_REQUIREMENTS.md)。

```mermaid
flowchart TD
    Upload[學生上傳自己的儀表板或修課紀錄] --> Ingest[資料匯入與解析]
    Ingest --> Audit[共用審查引擎]
    KB[入學年度規則庫] --> Audit
    Reviewed[承辦人覆核與抵修結果] -.-> Audit
    Audit --> Progress[個人進度與缺項]
    Progress --> Explain[白話說明與用語對照]
    Progress --> Action[需找承辦人辦理的事項]
    Progress --> Plan[修課規劃與 What-if]
```

1. 學生取得自己的修課資料，系統依其入學年度選用規則。
2. 審查引擎產生缺項，並標出校務系統可能誤判的情況：超修可移入其他類別、可重複修習的同課號、待辦抵修的停開課。
3. 以白話說明每項要求與系統代碼的意義，並列出需要找承辦人辦理的事項（抵修、抵免、人工認列）。
4. 需要時接入課程圖與規劃器，安排後續修課，模擬某門課不修或出國交換的影響。

學生端結果一律標示為「試算」，不是正式審查結果。學生只能查看自己的資料。

## AI、規則引擎、系辦與學生分工

| 角色 | 責任 |
|---|---|
| AI | 輔助解析與整理文件（儀表板、成績單）、依章則草擬規則庫供系辦確認、解釋審查結果、整理批次審查待辦、提供問答 |
| 規則引擎 | 按明確規則計算採計學分、判定要求是否滿足、輸出依據 |
| 系辦 | 確認正式規章、疑義、抵免及特殊核准，完成最終業務確認 |
| 學生 | 提供並確認自己的修課資料，依試算結果向承辦人辦理抵修、抵免等程序 |

AI 說明以審查結果為依據，不自行更改學分或創造規章。AI 解析的紀錄與草擬的規則都要經驗證與人工確認才會進入審查。未確認的資料與規則假設需可見。

## 結果與可追溯性

| 現有狀態 | 語意 |
|---|---|
| `PASS` | 已建檔要求全滿足，無引擎識別出的待核對項目 |
| `FAIL` | 至少一項已建檔要求未滿足 |
| `WARNING` | 要求滿足，但含暫時採計的未核對本系課程 |
| `MANUAL_REVIEW` | 類別資料無法認列，需要人工確認 |

目前狀態優先序為人工審查、未達標、警示、通過；報告仍需展示所有缺項與待核對資料。

介面需分開顯示系統判定與系辦確認狀態。系統通過表示輸入符合已建檔規則，不表示已完成所有正式核定程序。

現有要求帶有來源引用；目標報告還需記錄適用年度、規則版本、資料來源及審查時間，覆核需保留確認人與處理內容。完整紀錄功能尚待建置。

## 已定案與待決事項

已定案：學校端與學生端雙端架構、四個核心能力、學校端兩個業務入口、兩端共用審查引擎、AI 輔助且規則負責判定、系辦處理疑義、規則依入學年度取用、先以資管系完成再推廣到規則明確的系所。

待決：承辦人覆核與抵修結果是否同步到學生端、學生端身分驗證方式、開課資料來源（課務組）、儀表板實際格式、校務欄位、介面技術、AI 服務、資料儲存與權限、覆核紀錄、匯出格式，以及各年度正式規則與特殊認列細節。

現況及規則假設見 [實作狀態](IMPLEMENTATION_STATUS.md)。
